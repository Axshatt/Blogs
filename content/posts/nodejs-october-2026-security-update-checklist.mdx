Your application can have an up-to-date lockfile and still be running on an outdated Node.js runtime.

That distinction matters this week. On **October 21, 2026**, the Node.js project published security releases for the 22.x, 24.x, and 26.x branches. The official advisory lists high-severity fixes, including a Brotli decoder memory-safety issue, DNS input validation, and TLS hostname-validation problems. This is a runtime maintenance task worth checking alongside your normal dependency updates. [Source: Node.js security advisory](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases).

This guide separates the published release facts from a suggested update workflow. It does not establish whether a particular application is exploitable; that depends on its code paths, inputs, and deployment.

## The versions released on October 21

The official release notes identify these security releases:

- **Node.js 22.23.4**, on the 22.x LTS branch. [Release notes](https://nodejs.org/en/blog/release/v22.23.4).
- **Node.js 24.22.1**, on the 24.x LTS branch. [Release notes](https://nodejs.org/en/blog/release/v24.22.1).
- **Node.js 26.12.1**, on the 26.x Current branch. [Release notes](https://nodejs.org/en/blog/release/v26.12.1).

These are the versions announced for this release, rather than a promise that they will remain the newest patches. If you are reading later, check the latest release within your chosen supported branch.

As of this article's publication on October 23, the Node.js release page lists 22 and 24 as LTS and 26 as Current. Node.js recommends Active LTS or Maintenance LTS for production applications. Do not turn a patching task into an unplanned major-version migration. [Source: Node.js release status](https://nodejs.org/en/about/previous-releases).

## What the advisory actually says

The advisory identifies **CVE-2026-111497** as a high-severity Brotli decoder out-of-bounds write that permits remote code execution. It lists 22.x, 24.x, and 26.x as affected branches. It also describes DNS names containing NUL characters, several TLS validation issues, and additional HTTP, crypto, and permission-model fixes. The exact branch coverage differs by issue. [Source: official advisory](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases).

Avoid flattening that into “every Node app can be remotely compromised.” The advisory establishes affected runtime branches and vulnerabilities. Your own exposure assessment still needs to identify which functionality the application uses and what inputs can reach it.

For most small teams, my recommendation is to prioritize a tested runtime patch rather than spend the entire maintenance window trying to prove that every affected path is unreachable.

## First, find the runtime you are actually using

Run these commands in the environment you want to inspect:

```bash
node --version
npm --version
node -p "process.execPath"
node -p "JSON.stringify(process.versions, null, 2)"
```

`process.execPath` identifies the executable for the current process, and `process.versions` exposes Node.js and component version information. That makes them useful when several installations exist on the same machine. [Source: Node.js process documentation](https://nodejs.org/api/process.html).

The important phrase is **in the environment you want to inspect**. A terminal on your laptop cannot tell you which binary an already-running production worker is using.

My suggested inventory has four rows:

1. **Local development:** the runtime used to install, build, and run the app.
2. **Continuous integration:** the runtime selected by the workflow or runner image.
3. **Build environment:** the runtime used by the hosting platform to produce the deployment.
4. **Application runtime:** the process, function, worker, or container that handles live requests.

Record the observed version and where its configuration lives. Treat “not checked yet” as a real result instead of assuming that all four match.

## Why npm audit is a separate check

`npm audit` submits dependency information to the configured registry and reports known vulnerabilities in that dependency tree. Its documentation also explains the behavior of `npm audit fix`, including changes that may require manual review. [Source: npm audit documentation](https://docs.npmjs.com/cli/v11/commands/npm-audit/).

For this incident, a clean dependency report is not evidence that the Node executable has been patched. Updating an npm dependency and replacing the runtime are different operations.

Use both checks for their own purposes:

```bash
node --version
npm audit
```

I would not start a runtime security update with `npm audit fix --force`. Keep unrelated dependency changes out of the first patch so that a failing test has fewer possible explanations.

## A practical update workflow

The following steps are my recommended maintenance process, not additional instructions from the Node.js advisory.

### 1. Capture the starting point

Record the current runtime version, deployed commit, installation method, and the command used to start the service. For a container, also record the image reference or digest.

Check whether the app depends on a native addon, a custom certificate setup, an outbound proxy, or a worker process. Those details help you choose useful smoke tests after the update.

### 2. Patch within your supported branch

Use the installation mechanism your project already follows: a version manager, your hosting platform's runtime settings, a container image, or your operating system's supported package source.

For example, **if nvm is already your version manager** and your application is intentionally on Node 24, these commands select the October security release:

```bash
nvm install 24.22.1
nvm use 24.22.1
node --version
```

This example is deliberately pinned to the release discussed here. For future maintenance, choose the newest appropriate patch in your supported branch and check the project requirements before changing major versions.

Do not assume that changing one version file updates your CI workflow or hosting configuration as well. Check each place identified in the inventory.

### 3. Reinstall and test using the selected runtime

For an npm project with a committed lockfile, my suggested validation sequence is:

```bash
npm ci
npm run build
```

Run the project's test suite too, using the scripts it actually defines. A repository without a test script still needs a deliberate smoke test; a successful build does not exercise every request path.

Useful checks include:

- A normal page or API request.
- Authentication and session behavior, where present.
- Outbound HTTPS calls to real dependencies in a test environment.
- Upload and compression-related flows that the application actually implements.
- Background jobs, queue workers, and scheduled processes.

Record what you tested. “The home page loaded” and “the payment webhook passed its staging checks” are very different levels of evidence.

### 4. Rebuild and redeploy

For a containerized application, update the selected base image and rebuild the application image. Restarting an existing container is not a substitute for verifying the Node binary inside the replacement image.

For a managed platform, inspect its runtime configuration and deployment logs. A platform may manage patch selection itself; use its documented behavior and verify the outcome instead of assuming that the same control exists on every host.

If your application has separate web and worker services, check both. The web deployment can succeed while a long-running worker remains on the previous environment.

### 5. Verify the running replacement

After deployment, confirm the application responds correctly and inspect the version from the deployed environment through your platform's console or private operational logs.

Avoid adding an unauthenticated diagnostics endpoint just to display process details. You need evidence for maintenance, not a permanent public inventory of your server.

My minimum completion record would contain the deployed commit, the observed runtime version, the deployment time, and the result of the smoke tests. Keep a known-good rollback path, and remember that rolling back an entire old image may also restore the old runtime.

## Common mistakes to avoid

- **Updating only the laptop.** The app's production environment needs its own verification.
- **Changing major versions unnecessarily.** Separate compatibility work from a focused patch where possible.
- **Treating a version label as evidence.** Check the actual running process or deployed image.
- **Mixing many unrelated fixes.** Keep the change understandable enough to review and recover.
- **Claiming the application is now fully secure.** A runtime patch addresses a particular set of issues, not every weakness in the app.

## A useful student project extension

If you maintain several portfolio projects, build a small **runtime inventory checker** as an exercise. Have it read explicitly selected repository configuration files and report the declared Node major version, the source of that declaration, and whether it disagrees with another configuration in the same repository.

Keep declared versions and observed runtime versions in separate fields. A checker that reads a Dockerfile cannot prove what is currently deployed.

Add tests for missing configuration and conflicting declarations, then document those limits in the README. That produces a practical engineering artifact without pretending to be a comprehensive security scanner.

## Before you close the maintenance task

Confirm that the environments you operate use the intended patched runtime, your build and relevant tests pass, and the replacement deployment has been checked. Save the evidence alongside the change.
